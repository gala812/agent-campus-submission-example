# 01 需求与成功标准

## 用户与业务问题

用户是查询制度和产品能力的员工。核心问题是“能否找到当前资料支持的答案，以及资料不确定时能否明确说明”，而不是保证每个问题都有答案。错误回答制度或编造产品能力会误导后续工作。

题号：3，企业知识问答 Agent。用户具有科研问答背景，因此选取能迁移检索、证据引用和答案验证经验的题目。

## 输入与资料

- 必填question；可选history（最多12条，仅user/assistant）。空问题返回待澄清。
- 合成制度与产品FAQ，每份包含唯一ID、版本日期、标题、主题及原文。
- 文档检索与原文读取均为本地只读工具；真实模型通过HTTP选择动作。
- 测试可以注入工具故障或替换知识库；真实模式不读取测试预期答案。

## 交付与范围

交付CLI、源码、可执行测试、合成资料、至少三组实际输入/输出/Trace、五份文档、配置样例和Git提交。核心输出为回答、引用ID/版本/原文、资料缺口、冲突与状态。

不包含UI、线上部署、权限系统、真实企业资料、长期会话记忆、向量服务、多Agent或发布能力。范围控制以核心链路和可核验效果为先。

## 验收映射

| 题目要求 | 用例 | 预期行为 |
|---|---|---|
| 明确答案 | normal | 读取P01，支持自动中文字幕的结论附原文 |
| 文档冲突 | conflict | D01=30天，D02=15天；补查范围/优先级，无依据时请求确认 |
| 资料外问题 | out_of_scope | 不猜测火星氧气配额，报告资料缺口 |
| 改写相似问题 | paraphrase | “人声变成屏幕文字”仍找到P01 |
| 上下文追问 | followup | 理解“它”为星剪，重新读取并回答SRT/MP4 |
| 工具失败 | tool_failure_recovery / tool_failure_stop | 观察错误、保留成功检索、恢复或明确停止 |
| 信息不足 | missing_information / partial_evidence | 指代不明先追问；缺效果数据不编数字 |
| 更换文档核验 | changed_document / single_policy | P01变成不支持后答案变化；只有D01时可据30天回答 |
| 有界执行 | step_limit / tool_limit | 明确incomplete_limit，不伪装成功 |

## 成功标准

1. 安装步骤简短，离线入口不要求API密钥。
2. 真实模式至少出现两条不同工具结果驱动的动作路径，并保存实际Trace；Mock不用于证明这一点。
3. 六项题目验收与通用异常要求都有输入、实际输出和可复现断言。
4. 引用不允许来自未读文档、不匹配版本或伪造片段。对语义支持性另作审阅，不把溯源等同于语义正确。
5. 达到上限、工具失败、模型失败和资料不足都有明确状态。
6. 如实保留失败、未完成部分、实际时间和AI参与情况。
